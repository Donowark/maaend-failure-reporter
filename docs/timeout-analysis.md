# v0.3.0 超时诊断依据

## 已确认的现象

2026-11-07 的 v0.2.0 报告中，`/api/config` 连续三次在约 10 秒时触发 `Client.Timeout exceeded while awaiting headers`，累计 32.005 秒。程序执行了重试，但读取任务状态之前就退出了。

报告没有 TCP/请求发送的阶段记录，也没有其他接口结果、主机日志或 MaaEnd/MXU 版本，因此不能据此断言 API 变化、配置锁死锁或等待外部程序导致循环等待。

## 代码中确认的薄弱点

导出器 v0.2.0 串行执行 config → maa/state → interface。配置只负责列表/任务名称，却成为状态读取的前置条件；配置接口独立阻塞时，实时状态即使可用也不会被尝试。

MXU 当前源码仍保留 `/api/config`，并新增 `/api/config/snapshot`。配置处理器读取共享锁；状态处理器同样获取多把共享锁并调用后端运行状态。因此服务端锁等待、同步后端调用或服务线程受阻是合理待验证方向，但共享锁的存在不等于已证明死锁。

MXU 可能在默认端口占用时使用后续端口。本工具继续遵守用户指定端口，不擅自选择另一个实例；应核对日志中的 `Web server listening` 和设置中的实际地址。

## 此次修复

先读取本次实时状态并记录时间；主配置接口不可用时尝试配置快照，再尝试先前保存的显示元数据。缓存只保存列表/任务 ID、显示名称和顺序，绝不保存运行状态或完整配置。无法匹配的失败 ID 仍保留，缓存名称可能过时会明确提示。

未取得实时状态时始终失败；使用历史结果、猜测列表名或后台延迟导出都会混淆本次运行，因此没有使用这些方式。

增加连接阶段记录及独立接口探测：

| 新报告现象 | 更值得检查的方向 |
| --- | --- |
| TCP 连接失败 | 服务未启动、端口变化、本机拦截 |
| TCP 成功、请求已发送，多个接口都无首字节 | 整体服务阻塞或错误端口上的异常实例；不能单凭此判定死锁 |
| 配置接口失败，状态接口成功 | 配置路由/配置锁问题；本版可降级导出 |
| 状态接口失败，其他接口成功 | 状态锁或后端运行状态调用；仍需主机日志 |
| HTTP 404 / 格式不兼容 | 版本、接口路径、数据结构或错误服务 |

## 验证与限制

模拟测试覆盖配置持续不响应但状态可用、备用快照恢复、缓存中历史失败不泄漏、无缓存保留失败 ID、状态接口阻塞拒绝历史结果、所有接口阻塞分类、缓存端口隔离和重复 ID 校验；保留既有状态筛选与超时重试回归。

这证明了修复处理的故障模型，不证明用户机器上的底层原因，也不保证服务整体阻塞时仍能导出。若再次失败，请提供新版异常报告、同一时段 `debug/logs/mxu-tauri*.log` 及 MaaEnd/MXU 版本。发布包不包含用户的原始报告或日志。
